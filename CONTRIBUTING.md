# Как вносить изменения в репозитории QodeXSignall

Правила общие для всех репозиториев организации. Если в конкретном репозитории
есть свой `CONTRIBUTING.md`, он главнее.

## Один раз: форк и хуки

1. Сделайте fork репозитория в свой аккаунт GitHub и склонируйте форк.
2. Добавьте оригинальный репозиторий как `upstream`:
   ```bash
   git remote add upstream https://github.com/QodeXSignall/<repo>.git
   ```
3. Поставьте pre-commit, он будет проверять код при каждом коммите:
   ```bash
   pip install pre-commit
   pre-commit install
   ```

## На каждую задачу

1. Обновите основную ветку и создайте от неё новую. Основная ветка называется
   `main` или `master`, смотрите в конкретном репозитории:
   ```bash
   git fetch upstream
   git checkout -b fix/отчёт-не-сохраняется upstream/master
   ```
   Префикс ветки: `fix/` для исправлений, `feat/` для новой функциональности,
   `chore/` для обвязки и зависимостей, `docs/` для документации.
   После префикса — два-три слова о сути задачи. Номеров у карточек нет,
   поэтому с задачей ветку связывает ссылка в PR.
2. Вносите изменения и коммитьте как удобно. При коммите сработают хуки:
   часть проблем они исправят сами, коммит при этом прервётся. Посмотрите
   вывод, сделайте `git add` изменённых файлов и повторите коммит.
3. Запушьте ветку в свой форк и откройте Pull Request в оригинальный
   репозиторий. Заполните шаблон и обязательно вставьте ссылку на карточку:
   PR без неё не рассматривается. Один PR равен одной задаче; если изменений
   больше нескольких сотен строк, разделите на несколько PR.
4. В PR автоматически запустится проверка. Пока она красная, PR не
   рассматривается. Что именно упало, видно во вкладке Checks.
5. На комментарии ревью отвечайте правками в той же ветке, новые коммиты
   попадут в PR сами. Несколько кругов правок — это нормально.

## После мержа

Ветка сливается через squash: в основную ветку попадает один коммит
с заголовком PR. Поэтому:

- заголовок PR должен быть осмысленным: `fix: отчёт не сохранялся при пустом
  списке`, `feat: экспорт в Excel`, `chore: обновить зависимости`;
- влитую ветку удалите и больше не используйте;
- обновите форк кнопкой Sync fork на GitHub или командами
  `git fetch upstream && git checkout master && git merge --ff-only upstream/master`.

## Сдача работы

Мерж PR задачу не закрывает. Когда изменение работает на сервере, напишите
в описании карточки короткий отчёт: что сделано и как это проверить.
Желательно приложить скриншот результата. Дальше всё зависит от того,
кто завёл карточку:

- **другой человек** — переведите карточку в «Ждём ответа», в чате тегните
  автора, приложите ссылку на карточку и напишите «готово, забирай».
  Результат проверяет и переводит карточку в «Готово» автор;
- **вы сами**, потому что задача пришла к вам напрямую, — закройте карточку
  сами. Обращение закрывается после подтверждения заявителя.

## Чего не должно быть в репозитории

Пароли, токены, ключи, файлы `.env`, дампы баз. Настройки передаются через
переменные окружения, пример лежит в `.env.example`. Если секрет попал
в коммит, сообщите сразу: его нужно ротировать, а не просто удалить из истории.
